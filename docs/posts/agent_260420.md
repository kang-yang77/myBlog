# Harness Engineering 总结

## 1. 什么是 Harness Engineering？

如果说：

- **Prompt Engineering** 是直接优化提示词，让模型“更会回答”
- **Context Engineering** 是给模型补充正确且足够的上下文，让模型“知道该依据什么回答”
- **Harness Engineering** 则是为模型外面再加一层**控制系统**，让模型“在正确的流程里工作，并且输出可验证、可恢复、可协作”

所以，**Harness Engineering 不只是“加约束”**，更准确地说，它是：

> 围绕 LLM/Agent 构建一套外部运行框架，用流程、状态、规则、检查、记忆和交接机制来提升任务完成质量与稳定性。

它关心的不是“这一句提示词怎么写”，而是：

- 任务如何拆解
- 状态如何保存
- 过程如何约束
- 结果如何校验
- 多个 Agent 如何协作
- 上下文满了之后如何继续做下去

---

## 2. 为什么需要 Harness Engineering？

当任务变长、变复杂后，只靠 prompt 往往会遇到几个典型问题：

1. **上下文越来越长，模型开始失去连贯性**  
   前面看过的内容太多，后面容易遗忘重点，或者开始重复、跑偏。

2. **模型缺少稳定的过程控制**  
   即使模型某一步做对了，也不代表整个流程会持续正确。

3. **状态只存在聊天记录里，不可复用、不可恢复**  
   一旦开新窗口、换新 Agent、上下文被压缩，之前的工作就容易丢失。

4. **模型会“看起来做完了”，但其实没有真正完成**  
   例如提前收尾、漏做关键步骤、只完成表面任务。

因此，Prompt Engineering 解决的是“怎么说”，  
Context Engineering 解决的是“给什么信息”，  
而 Harness Engineering 解决的是“整个系统怎么跑”。

---

## 3. Harness Engineering 的核心组成

一个完整的 Harness，通常包含以下几层：

### 3.1 任务编排（Orchestration）
规定 Agent 应该按什么流程推进任务，而不是想到哪做到哪。

例如：

- 先澄清需求
- 再生成设计
- 再拆任务
- 再实现代码
- 再验证结果
- 最后归档记录

这本质上是在把“临场发挥”变成“标准流程”。

---

### 3.2 状态持久化（State Persistence）
把任务状态从“临时对话”转成“外部可读写的结构化记录”。

例如把这些信息写入文件或磁盘：

- 当前需求说明
- 已做决策
- 待办事项
- 当前阶段
- 下一步动作
- 已完成产物

这样即使：

- 换了一个新 Agent
- 开了一个新窗口
- 上下文被清空
- 任务中断后重启

系统仍然可以继续，而不需要重新读整个项目或重新理解全部历史。

---

### 3.3 约束与规则（Constraints / Policy Layer）
规定 Agent 在执行时必须遵守哪些边界。

例如：

- 不能跳过设计直接改代码
- 必须先读 spec 再实现
- 修改代码后必须同步更新文档
- 归档前必须记录影响范围
- 输出必须符合固定格式

这一层才是你原文里提到的“通过制定约束来规范模型输出”，  
但它只是 Harness Engineering 的一部分，不是全部。

---

### 3.4 检查与反馈（Validation / Feedback）
让系统不仅“生成”，还会“自检”。

例如：

- 测试是否通过
- lint 是否通过
- 设计是否和需求一致
- 文档是否同步更新
- 产物是否缺关键字段

没有这层，Agent 只能“生成内容”；  
有了这层，Agent 才能“生成 -> 检查 -> 修正 -> 再检查”。

---

### 3.5 交接机制（Handoff）
当一个 Agent 做不下去，或者需要切换 Agent 时，如何把任务完整交给下一个 Agent。

交接的关键不是“复制整段聊天记录”，而是输出**高价值、结构化、可继续执行的状态摘要**，例如：

- 当前目标
- 已完成工作
- 未完成工作
- 关键约束
- 风险点
- 下一步建议动作
- 相关文件路径

这就是长任务里非常关键的一种 Harness 设计能力。

---

## 4. Prompt / Context / Harness 三者的区别

### Prompt Engineering
核心问题：**怎么说，模型更容易按预期回答？**

关注点：

- 指令措辞
- 角色设定
- few-shot 示例
- 输出格式提示

适用场景：

- 单轮任务
- 短任务
- 结果主要取决于表达方式

---

### Context Engineering
核心问题：**给模型什么信息，模型才能做对？**

关注点：

- RAG
- Tool Use
- History
- Memory
- Skills
- 动态检索
- 上下文裁剪与压缩

适用场景：

- 任务依赖外部知识
- 多轮对话
- 长链条推理
- 代码库、文档库、历史记录参与决策

---

### Harness Engineering
核心问题：**如何构建一个外部运行框架，让模型持续、稳定、可控地完成复杂任务？**

关注点：

- 流程编排
- 状态落盘
- 规则约束
- 检查反馈
- 失败恢复
- 多 Agent 协作
- 任务交接

适用场景：

- 长时间任务
- 多步骤任务
- 代码 Agent / 软件开发 Agent
- 需要反复迭代和中断恢复的任务

---

## 5. 一个更准确的定义

可以把 Harness Engineering 概括为：

> Harness Engineering 是为 AI Agent 构建模型外部控制层的工程实践。  
> 它通过流程编排、状态持久化、约束规则、校验反馈和交接机制，让 Agent 在长任务、复杂任务和多 Agent 协作中保持稳定、可控、可恢复。

也可以用一句更口语化的话说：

> Prompt 决定模型这一轮怎么说，  
> Context 决定模型这一轮知道什么，  
> Harness 决定整个系统接下来怎么跑。

---

## 6. spec 框架为什么属于 Harness Engineering？

spec 框架的价值，不只是“写文档”，而是把任务推进过程变成一种**外部可管理的状态机**。

一个典型 spec workflow 可能包含：

1. 提出需求
2. 澄清边界
3. 形成设计
4. 拆解任务
5. 实现代码
6. 验证结果
7. 归档变更

如果这些信息都只是存在于聊天里，那么：

- 换窗口容易丢
- 换 Agent 需要重读
- 很难审计
- 很难协作
- 很难追踪“现在做到哪一步了”

而当这些状态被显式写入文件系统后，整个系统就从“对话式临场发挥”变成了“可恢复、可追踪、可协作的工程流程”。

所以，**spec 本质上不是单纯的文档规范，而是一种 Harness 载体**。

---

## 7. OpenSpec 这类方案的意义

可以把 OpenSpec 一类方案理解为：

> 用规范化的文件结构和工作流，把需求、设计、任务、实现、归档这些阶段的状态沉淀下来，供 Agent 在不同阶段读取、更新和延续。

它的关键收益在于：

- 不再完全依赖聊天上下文记忆任务状态
- Agent 不必每次都重新扫描整个项目
- 可以明确知道“当前处于哪个阶段”
- 可以在中断后继续推进
- 可以让多个 Agent 围绕同一套外部状态协作

换句话说，**它把“任务记忆”从模型脑内，迁移到了外部文件系统**。

---

## 8. 跨 Agent 同步机制

### 8.1 为什么需要跨 Agent 同步？

长任务里经常会遇到两个问题：

1. **上下文越积越多，模型连贯性下降**
2. **模型接近上下文极限时，容易提前收尾或表现异常**

因此，很多时候不应该让“同一个 Agent 一直硬撑到最后”，  
而应该在合适的时机：

- 清理上下文
- 启动一个新 Agent
- 把必要状态交接过去
- 让新 Agent 从结构化状态继续执行

这本质上是一种**会话级续跑机制**。

---

### 8.2 核心思想：不是继承全文，而是继承状态

跨 Agent 同步最重要的原则是：

> 不要试图把所有历史原样带给下一个 Agent，  
> 而是把“继续完成任务所需的最小充分状态”交给它。

应该同步的是：

- 任务目标
- 当前阶段
- 已完成事项
- 尚未完成事项
- 关键决策
- 风险点
- 文件位置
- 下一步动作

不应该同步的是：

- 全量闲聊历史
- 无关的中间推理
- 大量重复上下文
- 已经失效的信息

---

### 8.3 Simple Example

一个简单例子：

第一次 Agent 读完整个项目后，产出一份项目说明文档，例如包含：

- 项目目标
- 目录结构
- 核心模块
- 关键依赖
- 当前问题
- 已知约束
- 待办事项

之后如果开启一个新窗口或新 Agent，就不必再重读整个项目，  
只需要先读这份说明文档，就可以快速进入工作状态。

如果项目代码发生变更，再把这份说明文档同步更新即可。

所以，这份说明文档本质上就是：

- 项目的外部记忆
- 新 Agent 的启动上下文
- 多 Agent 之间的同步介质
- Harness 的一部分
